# 128K 与 256K 上下文实测

日期：2026-08-20

## 测试环境

- GPU：NVIDIA GeForce RTX 5070 Ti，16,303 MiB VRAM。
- 模型：`Qwen3.8-27B-UD-IQ3_XXS.gguf`。
- llama.cpp：build 10524，commit `9ee9fc04c`。
- 并发槽位：1。
- 模型层：全部 GPU offload。
- KV cache：K/V 均为 `q4_0`。
- Flash Attention：启用。
- Batch / ubatch：512 / 128。
- 测试方法：将唯一密钥置于提示开头，后接大量无关记录，在提示末尾要求只返回密钥；关闭 thinking，temperature 为 0。

## 结果

| 配置 | 实际 prompt tokens | 首部召回 | Prompt 吞吐 | 生成吞吐 | 请求耗时 | 显存余量 |
| --- | ---: | --- | ---: | ---: | ---: | ---: |
| 128K，短提示 | 1,003 | 通过 | 914.73 token/s | 47.13 token/s | 1.50s | 空闲约 1,247 MiB |
| 128K，长提示 | 120,012 | 通过 | 705.07 token/s | 11.72 token/s | 172.09s | 峰值约 1,022 MiB |
| 256K，短提示 | 1,003 | 通过 | 24.06 token/s | 0.52 token/s | 78.51s | 约 79–89 MiB |
| 256K，长提示 | 目标 245,000 | 未完成 | 稳定约 26.7 token/s | 未进入生成 | 主动终止 | 约 76–83 MiB |

256K 长提示在处理到 5,120 tokens 后主动终止。按已稳定的约 26.7 token/s 线性外推，仅 245K prompt 预填充就至少需要约 153 分钟；随着上下文增长，实际时间可能更长，因此没有继续占用机器数小时。

## 观察

- 128K 成功装载并完成 120K-token 首部信息召回，没有 OOM，短提示性能接近 8K 基线。
- 128K 在长提示尾部的生成速度降到约 11.7 token/s，但仍可用。
- 256K 可以装载，但 llama.cpp 明确警告无法满足默认显存余量，因为 `gpu-layers=all` 被显式固定。
- 256K 几乎耗尽显存，并使短提示 prompt 吞吐比 128K 慢约 38 倍、生成吞吐慢约 91 倍。
- 256K 的问题不是模型上下文能力或短提示召回准确性，而是当前 16GB GPU 上的显存边界和由此产生的严重性能退化。

## 结论

本机建议最大使用 128K。256K 全 GPU 配置只能视为“可装载”，不适合作为常驻服务。测试结束时曾恢复项目原有的 8K 配置；随后根据用户确认，常驻配置已改为 128K（131072 tokens），并发保持为 1。
